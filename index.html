A shared build kit for Airtable Interface Extensions

Not an app — a monorepo of design tokens, presentational primitives, and defensive data-access helpers, plus nine working extensions that consume them. Built to give every custom interface element the same Airtable-native look and the same guardrails against the beta SDK's sharp edges.

/overview

What this repo is actually for

Airtable's Interface Extensions SDK lets you embed custom React components directly inside an Interface Designer page — things the native chart and dashboard elements can't do. This repo is the reusable half of that work: the parts that would otherwise get rebuilt from scratch every time you start a new extension get pulled into packages/, and each deployed extension in apps/ stays a thin wrapper around them.

You'd reach for it whenever a specific Airtable base needs a bespoke visual — a gallery, a pivot summary, a chart shape Airtable doesn't ship — and you want it to look and behave like it belongs, without re-deriving Airtable's color palette or re-solving "what happens when a field isn't exposed to this interface" each time. It is not a general-purpose product you install once and sell to many customers: Airtable currently ties each built extension to the single base/interface it was created in, so the leverage here is in shared source code and shared judgment calls, not a shared deployed artifact.

/packages

The shared layer

@claude-code-interfaces/tokens

tokens

Airtable's real palette (11 hue families × 5 shades, sourced from the community toolkit) plus a spacing scale, radii, and a type scale — so extensions can match native Airtable styling without depending on the beta SDK's own colors/colorUtils export.

@claude-code-interfaces/primitives

primitives

Presentational components only — none import the Airtable SDK, callers wire in data and writes.

  • Badge — tone or raw select-field color
  • EditableText — click-to-edit, caller owns the commit
  • LinkedRecordPills — resolved link chips, optional remove
  • DebugPanel — collapsible JSON inspector for dev
@claude-code-interfaces/helpers

helpers

safeField.ts wraps getCellValue / getFieldByIdIfExists in try/catch. It exists because interface extensions only expose fields explicitly added to the interface's Data panel — and only the first four are visible by default. Every app in this repo reads fields through it rather than the SDK directly.

/constraints

What the beta SDK won't let you do

From docs/interface-extensions-sdk-research.md — the reason several design choices above look defensive.

ONE BASE ONLY

A deployed extension is tied to the base/interface it was created in. There's no confirmed way to install one build across many bases — reuse stops at the source level, which is the whole reason packages/ exists.

FIELD VISIBILITY

Only fields explicitly added to the interface's Data panel are readable, and only the first four are visible by default — silent failures otherwise, which is what helpers/safeField.ts guards against.

PLACEMENT

Dashboard or standalone interface pages only — no blank pages, forms, or record-detail views, and not viewable on mobile at all.

NO SECRETS

Anything in client code is visible to every viewer of the interface. The unused pat custom property wired into gallery and test is deliberately inert until routed through a backend you control.

NO UPLOADS

Attachment fields need a public URL — there's no direct binary upload from inside an extension.

PLAN GATED

Team, Business, or Enterprise Scale only. Disabled entirely on the Free plan, for builders and viewers alike.

Hard numbers — from .claude/skills/airtable-extensions/SKILL.md
COLOR PALETTE

Badges, tags, and select-field rendering are locked to Airtable's 10 hue families (blue, cyan, teal, green, yellow, orange, red, pink, purple, gray) — no custom hex or arbitrary colors anywhere in an extension. That's the entire palette packages/tokens exports, and all it can export.

WRITE RATE

15 writes/sec, global across every table in the base — not per table. Airtable auto-merges consecutive updateRecordAsync calls to the same table into one request to help stay under it.

BATCH & PAYLOAD

50 records max per batch write operation, and 1.9MB max per individual write payload.

GLOBALCONFIG

150kB total, 1,000 keys max, 50 paths max per setPathsAsync call — relevant if an extension persists its own UI state (a view mode, a filter) instead of a custom property. None of the nine apps above do this yet.

RECORD READ CAP unverified

A ~10k-record cap on what useRecords can load is referenced in community material, but Airtable's own docs don't confirm the exact figure — worth checking in-product before leaning on it for a very large table.

/recommendations

Use it when — skip it when

Reach for this repo

  • A specific base needs a visual Airtable doesn't ship — cross-tab summary, image catalog with inline notes, a chart shape outside the native set.
  • You're building several such tools for the same workspace and want them to share a look without rebuilding it each time.
  • You're prototyping with Claude Code and want the SDK's known gotchas pre-loaded via the vendored SKILL.md.
  • The audience is desktop collaborators already inside that base's interface.

Look elsewhere

  • The tool needs to run across many bases or be sold to many customers — no cross-base install path exists yet.
  • Anyone will need it on mobile — interface extensions don't render there.
  • The feature needs client-side secrets, PII handling, or direct file uploads.
  • You need something stable in production today — this is an open beta SDK, versions have already shifted underneath it.
/workflow

Starting a new extension

One sequence, start to finish. Done the CLI setup before? Skip to step 1 — everything from there runs again for every new extension.

Set up the CLIonce per machine, skip if already done

Install the CLI globally, then create a Personal Access Token in Airtable with the block:manage scope and register it — step 5's block add-remote authenticates against this.

npm install -g @airtable/blocks-cli block set-api-key
Copy the templatestart here for every new extension

From the repo root — the directory holding this repo's top-level package.json and the apps/ and packages/ folders shown in /map above — copy apps/test into a new app directory, named for the extension you're building.

cd claude-code-interfaces cp -R apps/test apps/<extension-name>
Clear the old deployment state

A stray .block/ here would silently point the new extension at the wrong block.

cd apps/<extension-name> && rm -rf node_modules .tmp .block
Rename the workspace package

In package.json, so npm workspaces and any future imports resolve to the new app, not app-test.

"name": "@claude-code-interfaces/app-<extension-name>"
Get a real block ID from Airtabledo this in the browser, not the CLI

The single most-skipped step. A blockId only exists once Airtable's servers create one for you — nothing local can generate a working one.

  • In the target base's Interface Designer, open a Dashboard/standalone page → Add a custom element → Create new extension (or the same from Builder Hub's Custom extensions list).
  • Airtable hands you either a ready-to-paste block init <baseId-or-NONE>/blk<realId> --template=... <dir> command, or creates the placement directly and shows its properties panel.
  • You only need the <baseId>/blk<realId> pair out of that — ignore the --template/new-directory part, since apps/<extension-name> from step 1 is already your scaffold.
Attach the app to that IDthe step that matters most

Run from inside apps/<extension-name>, using the real pair from the previous step. Extensions are permanently bound to whichever base/block they're attached to, so skipping this — or inventing an ID instead of getting a real one — leaves the app either pointed at the wrong base or at nothing at all.

cd apps/<extension-name> block add-remote <baseId-or-NONE>/blk<realId> live

This writes .block/live.remote.json in this app directory — the file step 2's rm -rf clears out on the next copy, and the reason it's gitignored (**/.block/*.remote.json) rather than committed.

Install dependencies

This is also what links the shared tokens/primitives/helpers packages in, via the CLI's sibling-directory bundling.

npm install
Preview it live

Start the local dev server against the remote from step 5, then in Interface Designer open the same custom element Airtable created there and click </> Develop, pointing it at the printed URL.

block run --remote=live

→ typically https://localhost:9000 — first load may need you to visit that URL directly once and accept the self-signed certificate warning before Develop will connect.

Ship it

Once it looks right, host the bundle on Airtable's infrastructure so other collaborators in that interface can use it without your dev server running.

block release
Why you can't invent a block ID: Interface Designer's "Add a custom element" list only shows extensions Airtable's servers already know about. A locally made-up blk... string — even paired with a real base, even accepted without error by block add-remote or block run — was never registered on Airtable's end, so it can't be attached to a page. This isn't hypothetical: it's what happened building gallery-editor in this repo's history before step 4 above was corrected to require getting the ID from Airtable's UI first.
Why step 5 can't be skipped either: reusing an old .block/remote.json across bases — even a real, registered one, just the wrong one — hits Airtable's other guardrail: {"error":"FORBIDDEN","message":"You can only run your development block in the original base where it was created."}
Where to find it afterward: every extension you've released — private or listed — shows up in Airtable's Builder Hub at airtable.com/create/extensions (Developers → Custom extensions), with its distribution status and last-release date. That's also where block release uploads end up.
